# Provenance-verified display translation

Status: PHASE 1 SHIPPED (project page + task page). Phases below.

## The problem

A project created from a playbook stores its title, description and
task text as literal strings in whatever language the organizer was
using. A member viewing in another language sees the organizer's
language — even though the app ships the exact same playbook text,
reviewed and gated, in their own. Eighteen languages are
content-complete; the gap is only in what happens *after* a template
becomes a project.

## The rule

**The app translates its own words, never yours.** A stored field is
rendered in the viewer's language only when it is *provably* the
app's own text: it must byte-match the shipped playbook corpus. Text
the organizer wrote or edited appears exactly as written, always.
Machine-translating member text is permanently out of scope — it
would mean sending members' words to someone else's computers, which
this app does not do.

## How verification works (and why it is safe)

Nothing in the record is trusted as a claim. Substitution happens
only when three keys agree, all checked client-side against the
app's own audited corpus:

1. **Template scope** — the project carries a `templateId` (already
   a signed, validated field; no schema change).
2. **Byte-exact match** — the stored string equals the template's
   text in *some* content language, compared against the shipped
   corpus (the eager `taskTitleIndex` for titles and template
   names; the lazily loaded content bundle of the matched source
   locale for descriptions). Near-match is NEVER accepted: "the
   organizer only fixed a typo" is exactly where the safety story
   dies, because a near-match displays words nobody signed.
3. **Row agreement** — a task title must match at exactly one task
   row (orders are parity-locked across locales, and a corpus gate
   pins task-name uniqueness within each template per locale), and
   its description is verified against that same row in the matched
   locale.

Security properties that follow:

- **Signed records are never altered.** Signatures still verify
  over the stored bytes; this is render-time substitution only,
  like rendering a date in the viewer's locale.
- **No forgeable claim exists.** A malicious record cannot make the
  app display words nobody wrote: the client only ever shows either
  the exact signed text or the shipped, reviewed translation of a
  template string the signed text provably equals.
- **Nothing leaves the device.** All display text comes from the
  app's own bundles. There is no translation service, no network
  call, no third party.

## Honesty on the surface

Substitution and disclosure are two halves of one contract:

- Substituted text is **marked once per surface** (not per string):
  a note in the why-idiom saying the text is shown in the viewer's
  language from the playbook, with a **View original** toggle that
  flips the whole surface back to the signed bytes. The toggled
  original carries the matched source locale's `lang` attribute and
  bidi isolation, so RTL/LTR mixing and the per-language
  line-height floors behave.
- When a surface mixes substituted and organizer-authored text, the
  note adds the second half: what the organizer wrote themselves
  appears exactly as written — the app never machine-translates
  member text.
- **Surfaces where exact words are load-bearing never substitute.**
  Dispute review, flag review, removals and exchange confirmation
  show signed bytes only. This is enforced structurally: an
  allowlist guard test asserts that only the phase-1 surfaces
  import the provenance hook.

## Phase 1 (this change)

- `content/templateProvenance.ts` — pure verification/substitution
  logic; `lib/useTemplateProvenance.ts` — the React hook (sync for
  titles via the eager index; async bundle-verify for
  descriptions, cached).
- `TEMPLATE_NAMES` joins the generated `taskTitleIndex.ts` (all
  content languages, like the task-name tables), regenerated by
  `scripts/generate-task-title-index.mjs` — which is now the ONE
  generator for that file; language-corpus assemblers run it
  instead of splicing JSON.
- Surfaces: **ProjectDetail** (title, description, task list) and
  **TaskDetail** (title, description), each carrying the marker +
  toggle. The project task filter matches both stored and
  displayed text so search-in-page stays coherent.
- Tests: verification unit tests (match, modified-field fallback,
  ambiguity, viewer==source no-op, async description verify), the
  corpus task-name-uniqueness gate, and the allowlist guard.

## What can go wrong, and the plan for each

- **Cross-locale false positive** (free text equal to a template
  string): bounded by the three keys above; the worst case
  displays the same template row's reviewed translation, which is
  semantically identical. Byte-exact only, whole field only.
- **Translation revisions orphan old projects** (GUARANTEED once
  native review lands — reworded template text stops matching
  projects created under the old wording): Phase 2 adds
  **append-only historical text/hash sets** to the generated index
  so prior wordings keep verifying while the *current* translation
  is displayed. Until then the fallback shows the original —
  honest, never wrong.
- **App-version skew across federation**: an unknown wording fails
  the match and falls back to the original. Safe degradation.
- **Unreviewed translations attributed to a person**: the marker
  does the attribution work — the app, not the organizer, owns the
  displayed translation, and the original is one tap away.
  Dispute/confirmation surfaces show originals regardless.
- **Search and downstream consumers** (board search, `.ics`
  export, print kits, gathering screen, read-aloud): Phase 2, each
  with an explicit decision — board search should match stored AND
  substituted text; exports and print follow the exporting
  member's rendering; read-aloud speaks substituted text in the
  viewer's voice and originals in the matched source locale's
  voice via per-element `lang`.
- **Fuzzy-match creep**: byte-exact or nothing is a NEVER, stated
  here so a future "optimization" has to argue with this document.

## Phase 2 (not in this change)

- Historical wording sets in the generated index (pre-native-review
  prerequisite — ship before the first reviewed-language reword).
- Board/MyWork/calendar/gathering-screen substitution + the search
  index decision.
- FAQ + member-guide entries stating the rule ("the app translates
  its own words, never yours") — content-tier, so it rides the
  full 18-language content pipeline as its own change.
- Event templates: `Event.templateId` exists; the same mechanism
  applies to event titles/descriptions.
